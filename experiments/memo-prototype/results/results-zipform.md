# Zipform benchmark: boss-literal zipWith kernel vs the combineOp kernels

All runs on the PR-165 PeTTa runtime (`/home/yab/PeTTa-pr165/run.sh`, commit
`b1f6f49`), sequential (never parallel), 5 reps per cell, invoked by
`run-bench-zipform.sh` from drivers generated by `gen-driver-zipform.py` out
of `driver-template-zipform.metta`. Raw logs:
`results/raw/<workload>_zipform_<S|M|M_content>_rep<i>.log` (+ `.time.txt`
per-rep bash-`time` process cross-check). Parsed by
`parse-results-zipform.py`.

**Timing method.** Identical to `results/results.md`: in-script
`(current-time)` markers (`BENCH_T0`/`BENCH_T1`) wrap ONLY the candidate fold
(replay iteration by index + scoring + checksum accumulation), excluding
process startup, imports, replay loading, and table installation. Each rep
additionally wrapped in bash's `time` builtin (no GNU `/usr/bin/time` on this
machine, so no max-RSS).

**Scoring path per candidate** (the thing being benchmarked):

- `zipform_S`: `(evalZipTermCached (rewriteTreeCached $e))` — hand-rolled
  `&space` caches for BOTH the rewrite (formula → materialized zip term,
  `&rewriteTermCache`) and the eval (zip subterm → column,
  `&zipSubtermCache`).
- `zipform_M`: `(evalZipTerm (rewriteTreeCached $e))` — lib_memo for both
  (`memoize rewriteTreeCached 1`, `memoize evalZipTerm 1`), wtinylfu,
  unique-limit 100000 (unbounded-equivalent: max observed keys per function
  is 2304), size-limit 5.
- `zipform_M_content` (bonus, majority3+mux6 only): as M, but a DRIVER-LOCAL
  evaluator variant routes every binary `zipWith` node through a separately
  memoized `(zipEval $f $colA $colB)` (`memoize zipEval 3`) so the combine
  step is keyed on actual column VALUES (content-addressed) rather than the
  zip-subterm expression. See the bonus section for exactly what this
  measures.

**Pre-matrix correctness gate.** The mandatory majority3 smoke test initially
FAILED (checksum 1204 vs required 3977) on both variants identically, traced
to a bug in `zipform/rewriter.metta`'s arity-1 branch (singleton AND/OR
wrapped through unary `zipWith1` with the *binary* builtin row-fn, silently
producing `(partial and (...))` terms). The module was fixed outside this
benchmark task (arity-1 foldable ops now pass their single child through as
identity), both zipform correctness harnesses re-verified 13/13 on both
runtimes, and the smoke gates re-passed (3977) before any matrix cell ran.
All numbers below are post-fix.

## Zipform key counts vs the old subtree key counts

Predicted going in: binary nesting of n-ary AND/OR (foldZipRight emits one
`zipWith` node per fold step, so a k-ary node becomes k-1 cache keys where
the old kernel had 1) should produce MORE distinct cache keys. **Observed:
the opposite — fewer keys on every workload.**

| workload | old subtree keys (kernel-S/M, source-expr keyed) | zipform eval keys (observed misses, materialized-term keyed) | ratio | zipform rewrite keys (= distinct candidates) |
|---|---|---|---|---|
| majority3 | 398 | **290** | 0.73x | 192 |
| mux6 | 2618 | **2304** | 0.88x | 1125 |
| parity3 | 2420 | **1836** | 0.76x | 977 |
| rand12 | 1384 | **1258** | 0.91x | 652 |

The binary-nesting inflation is real but is outweighed by rewrite-side
normalization, which the old source-subtree keying never got:

1. **Singleton-wrapper collapse** (the arity-1 identity rule): `(AND ((OR
   ...)))` and the bare `(OR ...)` rewrite to the SAME materialized term, so
   they share one eval key. These singleton wrappers are pervasive in the
   MOSES candidate streams (crude count: 645/6630/16803/1043 `(AND ((`
   occurrences in the four replay files) — under source keying each wrapper
   level was its own key.
2. **Spelling canonicalization**: distinct source spellings with the same
   op/child structure after rewrite (e.g. an `(AND (x y))` reached bare vs.
   inside a collapsed wrapper) merge onto one term.
3. **Fold-suffix sharing**: foldZipRight is right-associated, so candidates
   sharing a child-list *suffix* share the entire nested inner term as one
   key chain, partially refunding the k-1 inflation.

Net effect: 9-27% fewer distinct eval keys than the old kernels, and
correspondingly slightly *higher* hit-rates (e.g. majority3 0.805 vs 0.761).
Consequence for capacity planning: unique-limit sized off the OLD subtree
counts is safe (conservative) for zipform.

## The 2x2: cache mechanism (space vs memoize) x combine strategy (combineOp fold vs materialized zipterm walk)

Reading each workload as a 2x2 grid (kernel-S / kernel-M / zipform-S /
zipform-M):

**Axis 1 — cache mechanism — behaves the SAME under both combine
strategies.** The old crossover reproduces exactly inside zipform: space wins
on tiny columns (majority3: S 0.040 vs M 0.077; parity3: S 0.88 vs M 1.80),
mux6 is a wash within noise (S 1.24 vs M 1.55 median, bimodal), and memoize
wins decisively on huge columns (rand12: M 30.4 vs S 36.7, ~1.21x). The
combine-strategy change does not move the S-vs-M crossover point; column
size remains the controlling variable. (rand12's S-vs-M gap narrowed vs the
old kernels — 1.21x here vs 1.55x there — partly because zipform-M pays a
second memo dispatch per candidate that kernel-M didn't, and partly because
the old kernel-M cell ran under eviction pressure, see threats.)

**Axis 2 — combine strategy — what does the boss-literal form + generic
dispatch cost (or save)?**

- **On the space mechanism (cleanest comparison — both cells unbounded, both
  hand-rolled):** near-parity everywhere except parity3. majority3: zipform
  0.0398 vs kernel 0.0441 (~10% faster — fewer distinct keys to scan in the
  `match`-based cache, and 108 fewer column computations). mux6: 1.2425 vs
  1.2369 (wash). rand12: 36.71 vs 39.87 (~8% faster — 126 fewer 4096-cell
  column computations dominate). parity3: 0.8796 vs 0.6986 (~26% SLOWER,
  mins 0.81 vs 0.68) — parity3 is the highest-candidate-volume workload
  (7031), and zipform pays a per-candidate rewrite-cache lookup (a second
  `collapse (match ...)` over a 977-entry space) on top of the eval lookup;
  with 8-row columns there is no compute to amortize it against.
- **On the memoize mechanism:** zipform-M beats kernel-M on majority3
  (0.0770 vs 0.1216) but loses on parity3 (1.795 median / 1.19 min vs 0.9523
  median / 0.93 min) and rand12 (30.43 vs 25.75) — and both losing reference
  cells were *handicapped* by eviction pressure (limits 977/652 < their key
  counts) while zipform-M ran unbounded, so the true deficit is larger.
  Mechanism: every candidate costs TWO lib_memo dispatches (rewriteTreeCached
  + evalZipTerm) instead of kernel-M's one — 7031 extra memo probes on
  parity3, plus wtinylfu queue/sketch bookkeeping per store on twice as many
  functions.

**Bottom line:** the boss-literal materialized form is roughly cost-neutral
as a *representation* — its normalization even shrinks the key space 9-27%
and saves recomputation — but the extra rewrite *stage* it requires adds a
per-candidate cache-lookup toll. That toll is invisible where columns are
big (rand12) or streams are short (majority3), and is the dominant regression
where the stream is long and columns tiny (parity3, the pure-overhead
regime). Generic dispatch (if-chain on term head + var-headed builtin
row-fns) shows no measurable cost of its own beyond that: where the toll
doesn't bite, zipform matches or beats the specialized combineOp kernels on
the same mechanism.

## Content-addressed bonus cell (zipform_M_content)

**What was measured.** As zipform_M, but the driver defines a local
`evalZipTermCoreContent` (copy of `evalZipTermCore`'s structure; module files
untouched) whose only change is the binary-zipWith branch: children are
evaluated first, then the combine goes through `(zipEval $f $colA $colB)`
with `!(memoize zipEval 3)` — keys are the row-fn plus the two actual column
VALUES. Driver-local `change-state!` counters (incremented inside the
memoized bodies, which lib_memo only runs on a miss) give exact per-function
stats the global aggregate can't:

| workload | distinct zipWith subterms (CONTENT_CALLS) | distinct content keys (CONTENT_MISSES) | content-level dedup | median wall vs zipform_M |
|---|---|---|---|---|
| majority3 | 284 | 209 | 75 (26.4%) | 0.0844 vs 0.0770 (~10% slower) |
| mux6 | 2292 | 1945 | 347 (15.1%) | 2.1149 vs 1.5452 (~37% slower; mins 1.64 vs 1.37) |

(Counter identities verified exactly: majority3 aggregate 1992/691 = rewrite
722/192 + subterm-eval 1195/290 + zipEval 75/209; mux6 9104/5374 = 2673/1125
+ 6084/2304 + 347/1945. `memoize zipEval 3` behaved correctly — the
3-input-arg arity form worked first try, checksums OK, so the plan's
skip-if-misbehaving clause was not needed.)

**Finding: content addressing loses here, structurally.** The dedup is real
— 15-26% of distinct zipWith *expressions* compute a column some other
expression already computed — but the saving per content-hit is only the
final `List.zipWith` over two ALREADY-EVALUATED child columns (evaluating
the children is precisely what produces the key). Against that, EVERY
distinct zipWith node pays a 3-arg memo probe whose key contains two full
columns (8-64 cells here) — far heavier to canonicalize/hash than the
expression keys — plus an extra store for each of the 1945/209 distinct
content keys. Expression keying already captures the overwhelming bulk of
the reuse (hit-rates 0.72-0.81); content keying adds a second, more
expensive cache layer to capture the thin remainder. It could only pay off
if column-value collisions vastly exceeded expression collisions (e.g. many
syntactically different subtrees computing identical columns over big rows),
which these MOSES streams do not exhibit. The measured walls (slower on both
workloads, and with the gap growing with column size, since key weight grows
with rows) confirm it.

## Threats to validity

- **Translator echo overhead**: PR-165's runner echoes every top-level form
  (thousands of replay `add-atom` lines) with its Prolog translation; all
  stdout went to the raw logs. The in-script T0/T1 window excludes this
  entirely; it is a constant in the process-level `.time.txt` numbers only,
  and identical across variants on the same workload.
- **Machine noise, 5 reps**: single desktop, no isolation. mux6 and parity3
  reps are bimodal (~2x slow mode, e.g. mux6_S reps 1.21-2.53s), the same
  mode documented in `results/results.md`; medians there are
  contaminated, so per-rep minima are reported alongside. majority3,
  rand12, and majority3_M_content were stable (stdev/median <= 4% except the
  one slow majority3 rep in each of S and M).
- **Reference-row comparability**: the kernel-M reference cells for parity3
  (limit 977) and rand12 (limit 652) ran under eviction pressure, while all
  zipform_M cells are unbounded (limit 100000 >> 2304 max keys). This biases
  the kernel-M side of those comparisons SLOWER, which strengthens (not
  weakens) the conclusion that zipform-M regresses there. Reference numbers
  were also measured in an earlier session on the same machine/runtime, not
  interleaved with this run.
- **M stats are aggregates**: lib_memo's counters are global; the per-stage
  decomposition relies on the arithmetic identities above (all held exactly
  in every cell) rather than direct per-function counters, except in
  M_content where explicit body-side counters were added — which themselves
  add three `change-state!` operations per evaluated subterm, slightly
  inflating M_content walls (the majority3 M-vs-M_content gap of ~7ms over
  284 zipWith nodes is partly this instrumentation, so the content-keying
  penalty there is an upper bound).
- **Runtime pin**: all numbers on PeTTa-pr165 commit `b1f6f49`. No PeTTaV1
  timings (zipform_S would run there; lib_memo cells cannot).
- **Checksum strength**: total-True-count would not catch True-preserving
  cell permutations; exact-column correctness is covered by the two zipform
  harnesses (13/13 on both runtimes, post-rewriter-fix).
- **No memory data**: GNU `/usr/bin/time` not installed; max-RSS remains
  unmeasured. Zipform stores an extra cache (rewrite terms: 192-1125
  entries) that the old kernels didn't; unquantified.

## Variant R: reduce-dispatch, memoized combinators

A second eval backend for the SAME materialized zip terms (`zipform/rewriter.
metta`'s output is unchanged; only how it gets *evaluated* differs).
`zipform/evaluator-reduce-memo.metta` gives the term-language heads
themselves real, individually-memoized clauses (`col/1`, `fmap/2`,
`zipWith/3`, `zipWithN/2`), each dispatched via PR-165's `(reduce $term)`
head-only dispatch instead of `evaluator-common.metta`'s single `evalZipTerm`
function manually if-chaining on `car-atom` with an explicit `$eval`
recursion callback. Cache keys fall out for free as the raw, unevaluated
materialized subterm arguments — no separate "subterm" plumbing concept
needed. Rewrite-side caching (`zipform/rewrite-cache-memo.metta`,
`rewriteTreeCached`) is reused unchanged from variant M.

### Probe gate (`probes/probe-reduce-memo-combinators.metta`, PR-165)

All three questions resolved cleanly, no design changes forced:

- **Q1 (linchpin, memoize-on-unevaluated-args)**: a memoized 3-ary
  combinator reached via `(reduce $t)` on a cons-built term receives its
  args UNEVALUATED, and lib_memo keys on that raw structure correctly.
  Measured exactly: call 1 (miss) → `((cache_miss 1))`, independent
  side-effect counter `&colLookupCount` = 2 (both leaf columns actually
  resolved). Call 2, structurally identical cons-built term → `((cache_hit
  1) (cache_miss 1))`, `&colLookupCount` unchanged at 2 — the hit
  short-circuited before the body ran, so the children were never
  re-reduced. This is the exact mechanism the whole design depends on, and
  it holds.
- **Q2 (reduce-inside-memoized-body)**: confirmed both empirically (Q1's own
  child `(reduce $a)`/`(reduce $b)` calls dispatch correctly to `col`) and at
  the source level: `/home/yab/PeTTa-pr165/src/translator.pl`'s
  `reduce([F|Args], Out)` calls `resolve_runtime_call(F, Args, Out, Goal)`,
  which tries lib_memo's `metta_try_dispatch_call/4` hook FIRST — so a
  memoized function reached via `reduce` (whether as the top-level dispatch
  target or from inside another memoized function's body) is cached exactly
  like an ordinary call.
- **Q3 (zipWithN idiom + Grounded guard)**: `map-atom` + per-child
  `evalChild` (the one Grounded-guard helper: broadcast via `List.repeat` if
  `(get-metatype $c)` is `Grounded`, else `(reduce $c)`) works correctly on a
  mixed row op (two real column children + one constant `True` leaf),
  single-valued, correct column. **New finding, not in the original design
  note**: a literal `(reduce True)` (argument not a variable at translation
  time) is rejected by the translator's own `reduce` special-case with a
  syntax error before the program even runs. Through a let-bound variable
  (the only form `reduce` accepts, and exactly what `evalChild`'s own `$c`
  parameter receives at runtime), `(reduce $c)` on a Grounded value instead
  **fails silently with zero solutions** (a bare atom does not unify with
  `reduce`'s own `[F|Args]` list pattern) — not an error, just no output.
  This empirically confirms the Grounded-guard is mandatory, not defensive
  paranoia: an unguarded child-reduce site would silently drop rows whenever
  a sub-formula rewrites to a constant leaf (e.g. a nested zero-arity
  `AND`/`OR`).

No deviations from the design sketch were forced by any probe.

### Correctness harness (`correctness-harness-zipform-reduce.metta`, PR-165)

Mirrors `correctness-harness-zipform-memo.metta`'s 13 asserts exactly (same
reference formulas/columns, same table-switch staleness demo), scoring via
`(evalZipTermR (rewriteTreeCached $formula))`, plus 3 new asserts added per a
mid-task hardening requirement (duplicate/junk-value gates): a
`(size-atom (collapse (evalZipTermR ...))) == 1` check on the full parity3
result, a single-valuedness check on `(param zipTable)` after a table
switch, and a repeat of the size-atom-== 1 check on the final post-clear
result. **16/16 pass**, exit 0.

Root-level cache-shape assert (the one R-specific behavior the memo variant
can't exhibit, since it has one root memo entry and R has four independent
combinator caches): a second `evalZipTermR` call on the identical
already-rewritten parity3 term produced `(cache_hit 11)(cache_miss 18)` →
`(cache_hit 12)(cache_miss 18)` — **exactly +1 hit, +0 miss**, the same
shape as variant M's own root-hit proof. Under combinator-memoization there
is no single "root function" the way `evalZipTerm` is one function — the
cache unit for the second pass turned out to be exactly the outermost
`zipWith` node's own entry (parity3Formula's materialized term roots at a
`zipWith`, the outermost OR-fold step), and that one hit fully
short-circuited the entire subtree beneath it, matching Q1's proof.

**Junk/duplicate-value audit (explicit, per the hardening requirement)**:
grepped the full harness log for `partial` and `Error` — every occurrence is
either an echoed source-code definition (the dead `Error` clauses in
`combineOp`/`varColumn`/`memptyScan`/`rewriteTree`/`evalZipTermCore`, never
triggered) or lib_memo's own library-loader boilerplate string
(`partial(memoize,...)`, confirmed present identically in the already-passing
variant-M harness log too, i.e. unrelated to this variant). Zero occurrences
in any actual `RESULT`/`STATS`/structural-assert output line. All `test`
assertions (single-valuedness included) passed, so no duplicate solutions
were observed anywhere in this harness.

### Analysis: does combinator-granularity memoization beat the interpreter's single memoized entry point?

**No — it is roughly cost-neutral with M, not a clear win, and sometimes a
small loss.** majority3 (R 0.087 vs M 0.077 median, both mins close: 0.085 vs
0.077 — R ~13% slower) and mux6 (R 1.96 vs M 1.55 median — R slower, though
both cells are inside this environment's documented bimodal ~2x noise mode
for mux6/parity3, so the min columns — R 1.46 vs M 1.37 — are closer and more
trustworthy) both show R paying a modest tax rather than a saving. parity3
inverts this on the median (R 1.32 vs M 1.80 — R noticeably faster) but the
mins are close (R 1.29 vs M 1.19), consistent with parity3's own noise mode
rather than a real architectural win. rand12 — the workload where per-cache
dispatch overhead should be most washed out by real column-compute work
(4096 rows/column) — has R and M essentially tied (30.84 vs 30.43 median,
28.54 vs 28.64 min), which is the cleanest evidence: **when the dispatch
mechanism doesn't matter (compute-bound), R and M cost the same**, exactly
as expected since both ultimately route every memoized call through the same
lib_memo `metta_try_dispatch_call` hook and hit/miss the same key space.

Where R and M diverge (majority3, mux6), the direction favors M slightly:
plausible mechanism is that R pays FOUR independent lib_memo per-function
housekeeping paths (`with_cache_fun_mutex`, per-(Fun,Arity) generation
counters and WTinyLFU queues) where M pays one, adding a small constant
per-dispatch tax that only shows up when columns are small enough (8-64
rows) that dispatch overhead is a non-trivial fraction of total work — the
same "small columns expose fixed overhead" story `results-zipform.md`
already tells for the S-vs-M cache-mechanism crossover. There is no
compensating benefit from R's finer-grained caching here because the
*aggregate* key space M and R cache over is identical (same table above) —
R's four caches are a repartitioning of the same reuse, not additional
reuse.

**Bottom line**: reduce-dispatch as a *mechanism* is a viable, simpler-to-
read alternative to the `$eval`-callback pattern (no explicit recursion
plumbing — the combinator IS the recursion, and per-node cache keys fall out
for free from `reduce`'s head-only, unevaluated-children semantics) but it is
not a performance win over the existing single-memoized-function design at
these workload sizes; where it costs anything, the cost is a small,
plausibly-fixed per-dispatch multiplier from running four independent
memoization instances instead of one, most visible on the smallest-column
workload and washed out entirely on the largest.

**Additional threats to validity (R-specific, beyond the ones already
listed above for S/M)**: same machine/noise caveats apply (5 reps, no
isolation, mux6/parity3 bimodal). R's benchmark reps were run in the same
session as this report (not interleaved with the original M/S matrix, which
ran in an earlier session) — cross-session timing comparisons carry the
usual caveat that machine load may differ session to session, though the
rand12 near-tie with the recorded M numbers suggests the machine state was
comparable.

## Variant P: production-definitions (n-ary AND/OR/NOT clause dispatch)

The fourth combine strategy for the same replay streams: score candidates
through PRODUCTION-STYLE op definitions —

```metta
(= (AND $args) (all $args))
(= (OR  $args) (any $args))
(= (NOT ($x))  (not $x))
```

(`zipform/ops-nary.metta`, with local HOF-style `all`/`any`: `foldl-atom`
over the non-short-circuit builtin `and`/`or`, semantics copied from
production's `utilities/general-helpers.metta`, identities `(all ()) = True`
/ `(any ()) = False` preserved) — instead of variant M's monoid-fold +
`rowFnOf` mapping. The rewriter (`zipform/rewriter-nary.metta`,
`rewriteTreeNary` + `!(memoize rewriteTreeNaryCached 1)`) emits ONE
cons-built `(zipWithN $op (<rewritten children>))` node for EVERY op at
EVERY arity — no `foldr1`, no `fmap`, no `mempty`, no singleton collapse.
The evaluator is `zipform/evaluator-common.metta` +
`zipform/evaluator-memo.metta` REUSED VERBATIM (zero changes): its existing
zipWithN branch calls `($op $row)` per transposed row, and a call
`(AND (v1 .. vk))` has one argument — the tuple — which dispatches
`(AND $args)` directly (verified in `probes/probe-nary-endtoend.metta`
before anything else was built). Only the combine strategy + op definitions
differ vs variant M; caches, evaluator, timing method, streams, tables are
identical.

### The quote regime (what giving AND/OR/NOT real clauses cost)

Once `ops-nary.metta` is in scope, ANY bare `(AND ...)`/`(OR ...)`/
`(NOT (...))` literal in the same translation unit compiles as a live goal
call (whole-file prescan + import gating). Verified containment
(`probes/probe-nary-quote-store-retrieve.metta`): values bound from
space content via a quote-destructuring `match` pattern — and values passed
onward as plain function arguments — stay fully inert; only literal SOURCE
TEXT fires. Concretely, variant P had to quote:

- **The entire candidate corpus**: new `captures/<wl>.replay-quoted.metta`
  files (`scripts/capture-to-replay.py --quote`, a new opt-in flag; no-flag
  output re-verified byte-identical to the existing unquoted replay files,
  which are untouched). Driver-side retrieval destructures the wrapper in
  the match pattern: `(match &replayStream (candidate $i (quote $e)) $e)`.
- **Every reference formula in the correctness harness**:
  `common/reference-formulas.metta`'s getters return bare AND/OR/NOT
  literals, safe for every other variant but live here, so
  `correctness-harness-zipform-nary.metta` carries P-local `(quote ...)`
  twins of all 7 formulas (the expected COLUMN getters are plain
  True/False tuples and were reused verbatim).
- **Structural-assert oracles** (expected zipterm shapes) — same `quote`
  idiom every other zipform harness already needs for zipWith/col heads.

This is a real, recurring authoring tax: it silently corrupts (rather than
errors) when missed, and it is exactly the hazard class the production
codebase manages with its own quote conventions.

### Correctness harness (`correctness-harness-zipform-nary.metta`, PR-165)

### Key counts: the fewer-keys prediction was WRONG (and exactly why)

P's aggregate stats decompose exactly (rewrite share measured directly by a
rewrite-only probe over each full stream — misses = distinct candidates,
hits + misses = streamlen, all identities held):

| workload | P eval hits/misses | P eval hit-rate | M eval hits/misses (ref) | M hit-rate | old combineOp kernel keys (ref) | P keys vs M |
|---|---|---|---|---|---|---|
| majority3 | 1264/**398** | 0.761 | 1195/290 | 0.805 | 1264/398 | 1.37x MORE |
| mux6 | 6838/**2618** | 0.723 | 6084/2304 | 0.725 | 6838/2618 | 1.14x MORE |

The going-in hypothesis (P sheds M's fold-suffix keys, so fewer keys) is
refuted, and the numbers say precisely why: P's eval hits/misses are
IDENTICAL, cell for cell, to the ORIGINAL combineOp kernels'
source-subtree key counts. That is forced by construction — `rewriteTreeNary`
is a structure-preserving isomorphism (every source node ↦ exactly one
zipWithN node, every leaf ↦ one col node, nothing merged, nothing split),
so distinct materialized subterms == distinct source subtrees. P does shed
the suffix entries, but it ALSO sheds the two key-REDUCING mechanisms that
made M's key count low: singleton-wrapper collapse (`(AND ((OR ...)))`
merging onto `(OR ...)`'s entry — those wrappers are pervasive in these
MOSES streams) and the spelling canonicalization that collapse enables. M's
net was 0.73-0.91x the old kernel's keys; P lands exactly back AT the old
kernel's keys — 1.10-1.37x MORE than M, with correspondingly lower
hit-rates (e.g. majority3 0.761 vs 0.805 — exactly the old kernels'
hit-rates, as they must be, same key space).

### Analysis: what per-row clause dispatch costs vs columnar folds

P is the slowest variant measured in this whole experiment, on every
workload: 2.0x M on majority3, 2.6x on mux6, 1.18x on parity3 (mins 1.68 vs
1.19), and **3.8x on rand12** (116.5s vs 30.4s — and note P's rand12 stdev
is small; this is a clean, real gap, not noise). Three stacked mechanisms,
in increasing order of importance:

1. **More cache misses** (the key-count table above): every miss is a full
   column computation. Small effect — ~10-37% more misses.
2. **Transpose overhead on every node**: M's dominant path is binary
   `zipWith` → native `List.zipWith` walks two columns directly. P's ONLY
   path is zipWithN → `transposeCols` materializes a k-tuple per row (an
   O(rows x k) re-consing of all child columns) before any op runs.
3. **Per-row MeTTa clause dispatch — the dominant cost, and it scales with
   rows**: for every row, `($op $row)` is a var-headed reduce dispatch into
   a MeTTa clause (`AND` → `all` → `foldl-atom` closure over the tuple),
   where M's per-row work is one grounded builtin call (`and(A,B,R)` etc.)
   inside a native maplist. That is the difference between a Prolog builtin
   and an interpreted MeTTa function call, paid rows-times-nodes times. The
   workload gradient proves the attribution: parity3 (8-row columns) shows
   the smallest gap (1.18x), mux6 (64 rows) 2.6x, rand12 (4096 rows) 3.8x —
   the per-row toll grows linearly with column height while every other
   cost stays fixed.

### Recommendation

**Do not adopt the production-style n-ary definitions as the scoring
kernel's combine strategy.** Variant P is strictly dominated: slowest wall
time on all four workloads (up to 3.8x vs M on the biggest table, the case
that matters most), MORE cache keys and LOWER hit-rates than M (the
predicted key-count benefit inverted), plus a mandatory quote regime that
every file touching candidate data must observe on pain of silent
corruption — a real maintenance tax the other variants don't pay (their
AND/OR/NOT are inert data everywhere). Its one genuine virtue is
simplicity: the rewriter is 11 lines with no op tables, and op
extensibility is "write one clause" — but variant M's args-tuple
convention already provides exactly that extension path for new ops while
keeping AND/OR/NOT inert and the fast fold path for the ops that dominate
real streams. If alignment with production's definitions is ever required,
the sane shape is a thin translation layer at the boundary, not per-row
clause dispatch in the scoring inner loop.

**Threats to validity (P-specific)**: same machine/noise caveats as every
other section (5 reps, no isolation, mux6/parity3 bimodal — but P's gaps
exceed the noise mode on majority3/mux6/rand12, and rand12's stdev is
1.5% of median). P's reference comparisons are cross-session. The per-row
dispatch attribution rests on the row-count gradient, not a profiler.

## Variant G (generic ops: define AND/OR/NOT, drop rowFnTable) — 2026-07-22

**Hypothesis (user):** since the rewriter already folds candidates into nested
BINARY `zipWith` terms, define `AND`/`OR`/`NOT` at their row arity and let the
rewriter pass the op symbol straight through into `(zipWith $op ...)` /
`(fmap $op ...)`, so `rowFnOf`/`rowFnTable` disappear (adding an op = one
clause, zero rewriter edits). Distinct from variant P: P defined the ops at
arity-1 (n-ary `all`/`any`) and used uniform `zipWithN` per-row dispatch (2-3.8x
slower); G keeps the boss's monoid-fold structure and defines the ops at their
BINARY/unary ROW arity, so it stays on the fast nested-zipWith path.

**Why it works (the translator mechanism, probed 2026-07-22):**
`src/translator.pl` `build_call_or_partial` compiles `(F args…)` to a real call
only if a predicate `F/(argc+1)` exists, else to `partial(F,args)` — in goal AND
pattern positions. Defining `AND/2` therefore turns any arity-1 `(AND …)` into
`partial('AND',…)`. This is survivable because:
  - candidate DATA is arity-1 `(AND (children))`, which has NO matching clause
    (only `AND/2` is defined) and stays inert TO MATCHING when it arrives clean
    via `quote`;
  - the rewriter destructures with a VARIABLE head `(let ($op $children) …)`,
    never a literal `(AND $cs)` head — a literal head would itself compile to a
    `partial(...)` pattern that a clean quoted candidate can never unify with
    (probe-quote-and-destructure, probe-generic);
  - every literal `(AND …)` mention in loaded files (ops tables `monoids`/
    `memptyTable`, reference formulas, replay captures, inline harness
    candidates) is `quote`d so it stays clean data (probe-g-tables, probe-quote-
    head confirm quote-in-a-body yields a clean list; quote in a clause HEAD
    does NOT fire and is useless there).

**Correctness:** `correctness-harness-zipform-generic.metta` 13/13. Benchmark
checksums IDENTICAL to variant M on all four workloads (majority3 3977, parity3
30354, mux6 140043, rand12 3912064). Cache hit/miss counts byte-identical to M
(majority3 1917 hit / 482 miss) — G emits the same materialized terms as M, only
with the op SYMBOLS `AND`/`OR`/`NOT` where M emits the builtins `and`/`or`/`not`,
so the memo key structure and every subterm-sharing decision are unchanged.
**G does NOT undo the boss's approach** — same zipWith materialization, same
per-subterm caching.

**Performance (5 reps, PR-165, `BENCH_ELAPSED_SEC` scoring-loop only):**

| Workload | M median | G median | M min | G min | G vs M (min) |
|----------|----------|----------|-------|-------|--------------|
| majority3 | 0.079s | 0.076s | 0.074 | 0.074 | ~0% |
| parity3  | 1.21s | 2.23s† | 1.171 | 1.214 | +3.7% |
| mux6     | 1.40s | 2.23s† | 1.344 | 1.354 | +0.7% |
| rand12   | 29.96s | 30.55s | 28.96 | 29.24 | **+1.0%** |

†parity3/mux6 G reps were bimodal (system contention pushed some reps ~2×); the
MINIMA are the reliable compute estimate. rand12 (large, noise-robust) is the
cleanest signal: **G ~1% slower**; minima across workloads put G at +0.7%..+3.7%,
best estimate ~1-2%.

**Verdict: viable simplification, small measurable cost — NOT a performance win.**
G genuinely deletes `rowFnTable`/`rowFnOf`/`rowFnOfScan` and makes op-addition a
one-liner, at the price of (a) ~1-2% slower scoring from the extra per-row
`AND → and` indirection (the saved rewrite-time table scans don't recoup it —
rewriting is cached and a tiny fraction of the work), and (b) a PERVASIVE
mandatory `quote` regime across every file that mentions an op symbol (silent
`partial` corruption if any site is missed — the same fragility variant P
carried). Since the standing rule is "adopt only on a performance improvement,"
and there is none, this is presented for the user to decide: table (current,
fast, no quote discipline) vs generic defs (simpler op layer, ~1-2% slower,
quote-everywhere). Files: zipform/{ops-generic,rewriter-generic}.metta,
common/reference-formulas-quoted.metta, correctness-harness-zipform-generic.metta,
drv_*_zipform_G.metta, probes/probe-quote-and-{eval,destructure}.metta; raw
timings results/raw/bench-zipform-G-vs-M.txt.
